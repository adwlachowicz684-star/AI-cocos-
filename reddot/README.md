# reddot · 红点系统

## 它解决什么

"邮件有新的"、"任务能领了"、"商店上新了"——
这些小红点散落在几十个 UI 入口上。

手写在每个界面 `if (hasNewMail) showDot()`，会遇到：

1. **父子联动漏算** — 子项亮了但入口没亮，玩家觉得割裂
2. **计数对不上** — 子项显示 3、父项显示 1，玩家会问"还有 2 个在哪"
3. **清除时机混乱** — 点开邮件算已读，红点没重算，要重进界面才消失

## 用法

```typescript
const r = new RedDot();

r.set('mail/system', 3);
r.set('mail/gift', 2);

r.get('mail');      // 5 —— 父节点自动聚合，不需要手动维护
r.get('');          // 5 —— 根节点也是
r.any('mail');      // true —— 只判断有无，不聚合数量

r.override('quest', 2);    // 父节点显示自定义口径（如"可领取数"）
r.override('quest', null); // 取消覆盖，回到自动聚合
```

## ⚠️ 坑

| 坑 | 说明 |
|---|---|
| **根路径的 prefix 是空串** | 写成 `path + '/'` 的话根永远显示 0，表现为"子项都亮着、总入口没有" |
| **前缀不能误匹配** | `mail` 不该匹配 `mailbox`，前缀必须以分隔符结尾 |
| **`add` 先相加再夹** | 写成 `max(0, cur) + delta` 时 cur=3、delta=-10 会得到 -7 并抛错 |
| **缓存必须在任何修改后失效** | 否则"进过一次界面后红点数就不准了" |
| **通知要包含所有祖先** | 只通知叶子的话父节点不刷新 |
| **`override` 用于业务口径** | 比如"任务"页签想显示可领取数而不是子项总数 |

## 完整接口

| 成员 | 说明 |
|---|---|
| `set(path, count)` | 直接设置数量 |
| `add(path, delta)` | 增减（**先相加再夹**，见坑表格） |
| `clear(path)` | 清除**某个路径及其全部子路径** |
| `clearAll()` | 清空整棵树 |
| `get(path)` | 聚合后的数量（**含所有后代**） |
| `own(path)` | **该节点自己的数，不含后代** |
| `has(path)` | 该路径是否存在（有记录） |
| `any(path)` | 该路径或任一后代 > 0 |
| `children(path)` | 直接子路径列表 |
| `activePaths()` | 所有 > 0 的路径（**刷新 UI 用这个**） |
| `override(path, count)` | 覆盖父节点口径（`null` = 取消） |
| `exportState()` / `importState(s)` | 存档 |

> ⚠️ **`get()` 是聚合值，`own()` 才是节点自己的值。**
> 做"父节点显示 5、子项显示 3 和 2"的界面时，
> 父节点用 `get()`、叶子用 `own()`（叶子通常两者相等）。
> 全部用 `get()` 会让叶子和父级显示同一个数。

> ⚠️ **`clear(path)` 会连子路径一起清。**
> 只想清单个节点的话用 `set(path, 0)`——
> 但注意子路径还在的话，`get(path)` 仍会返回子项之和。

> ⚠️ **`any()` 与 `get() > 0` 不等价。**
> `any()` 在路径不存在时也返回 false 且不抛错；
> `get()` 对不存在的路径返回 0。
> 数值上一致，但 `any()` 语义更清晰且**短路更快**
> （找到一个 > 0 就返回，不用遍历整棵子树）。

> **`activePaths()` 是刷新 UI 的正确入口。**
> 遍历整棵树去判断哪些该亮红点，
> 既慢又容易漏——它已经过滤好了。

### `RedDotOptions`

| 字段 | 说明 |
|---|---|
| `separator` | 路径分隔符（**默认 `'/'`**） |
| `onChange(path, count)` | 数量变化回调（**含所有祖先**） |

> ⚠️ **`onChange` 会为每个受影响的祖先各触发一次。**
> 设 `mail/gift` 会连带触发 `mail` 和根节点——
> 在回调里做重的操作（重建 UI、发请求）会被放大成多次。

> ⚠️ **改 `separator` 会让已有存档的路径全部失效。**
> 换分隔符等于换了一套路径体系——
> 旧存档里 `'mail.gift'` 在新配置下是一个**扁平的单节点**，
> 不再是父子结构。要么别改，要么做迁移。

## 设计：为什么父节点自动聚合

父子不一致是红点系统最常见的 bug 来源。
让父节点 = 所有后代之和，业务只需要管好叶子，
父子关系在任何时刻都自洽。

需要不同口径时用 `override` 显式声明，
而不是在业务层自己算一个数塞进去——那样又会和子树失去同步。
