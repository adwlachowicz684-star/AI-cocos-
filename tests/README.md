# tests/run.ts —— 测试套件说明

## 结构

| 文件 | 内容 |
|---|---|
| `_framework.ts` | 迷你框架（describe / test / assert / eq / near / throws） |
| `run_core.ts` | 第一批 6 个插件（86 项） |
| `run_p0.ts` | P0 四个地基插件（87 项） |
| `run.ts` | 入口，依次跑上面两组并汇总 |

## 为什么不用 jest

jest 需要装依赖、配环境。这里用一个约 30 行的迷你框架，
你装个 TypeScript 就能立刻验证库是对的：

```bash
npm install
npm test          # 构建 + 跑 173 项测试
npm run example   # 跑第一批综合示例
npm run example:p0
```

## 迁移到 jest

每个 `test(...)` 可以直接改成 jest 的 `it(...)`，
`assert*` / `eq` / `near` 换成 `expect(...).toBe(...)` / `.toBeCloseTo(...)`，
**测试逻辑一行都不用改**。

## 测试重点的选择

**不要追求 100% 覆盖率。** UI 和渲染相关的自动化测试成本收益极差。
把精力放在**纯逻辑**上——那才是 bug 高发区。

| 优先级 | 被测对象 | 为什么 |
|---|---|
| 0 | **Scheduler 暂停语义** | 「暂停后 buff 仍在倒计时」是最让玩家愤怒的 bug，且完全不报错 |---|
| 1 | **RNG 可复现性** | 这是种子随机的核心承诺，破了整个游戏的可复现性就废了 |
| 2 | **伤害管线各阶段** | 数值错了不报错，只会悄悄偏差 |
| 3 | **Modifier 运算顺序** | 团队里两人理解不同，数值就会对不上 |
| 4 | **Track 区间查询** | 漏事件是时间轴播放器的经典 bug |
| 5 | **JoystickCore 边界** | 死区、归一化、松开归零——都是"看起来对但实际错"的地方 |
| 6 | **对象池生命周期** | 忘记 reset 是经典 bug |

## 这些测试真的抓到了 bug

写这套测试的过程中，抓到了 **5 个真实缺陷**：

**① Seed.encode / decode 往返不一致**

```
encode(12345) → 'TIGER-85'
decode('TIGER-85') → 2745   ← 不是 12345
```

原因：`check = floor(s/32) % 100` 丢掉了高位信息。
修复后明确了语义——**字符串才是种子的真身**，
用 `random()` 生成字符串，用 `decode()` 转数字，而不是反过来。

**② 极高护甲时伤害归零**

```
20 伤害 vs 99999 护甲 → 0.02 → Math.round → 0 → 被误判为"免疫" → 伤害 0
```

原因：免疫判定写在了取整**之后**。
修复：免疫判定必须在取整前用浮点值判断——
减免后 > 0（哪怕只有 0.02）就不算免疫，走保底给最低伤害。

### ③ `everyFrame` 被当成一次性任务（P0）

```typescript
// interval = null 在内部语义里是「一次性任务」，执行后删除
everyFrame(fn) → this._add(fn, false, 0, null, Infinity);   // ❌ 只执行一帧
everyFrame(fn) → this._add(fn, false, 0, 0, Infinity);      // ✅ 间隔为 0 的重复
```

现象：`everyFrame` 注册的回调只跑了一次。这个 bug 在真实使用场景下
会表现为「角色动一下就不动了」，且没有任何报错。

### ④ `beginFrame` 无条件覆盖模拟量（P0）

beginFrame 会重置所有轴（数字键状态每帧都要重算），
如果在它**之前**调用 `setAxisAnalog`，模拟量会被清掉。

现象：手柄摇杆完全没反应，但键鼠正常——很容易误判为"手柄没连上"。

修复：明确调用顺序（beginFrame → setAxisAnalog → 读取），
并专门加了一条测试来固化这个顺序。

### ⑤ `repeat` 的浮点累积误差（P0）

`1/60` 累加 30 次是 `0.4999999999999999` 而不是 `0.5`，
导致 `remaining > 0` 判断不通过，本该触发的那帧被跳过。

现象：1 秒 / 0.5 秒间隔的定时器只触发 1 次（少一次）。
这类误差在长时间运行下会累积成明显偏差。

> 这正是为什么数值与时间语义要写测试：**它不会报错，只会悄悄错。**

## 建议补充的测试

以下几个方向值得后续加（当前版本未覆盖）：

- **Scheduler 长期漂移**：跑 10 万帧后 scaledTime 与理论值的偏差

- **性能测试**：RNG 生成 100 万次的耗时、对象池高频 get/put
- **边界压力**：Track 有 1000 个事件时、地图生成器跑 10 万次
- **属性测试**（fast-check）：随机输入下不崩溃、不产生 NaN
- **跨平台**：不同 Node / 引擎版本下的浮点一致性
