### 额外加分：它发现原报告漏写了两个入口

P1-1 原报告只写了 dt 守卫一个入口。W1-B 实测发现**实际有三个**：

1. **dt 入口**：基线上**已经修好了** —— 源码是 `if (!(dtSec > 0)) return null;`（肯定式，能拦 NaN）
2. **dist 入口（真正开着的）**：`if (dist < this._minDist)` 是否定式，`NaN < x` 恒 false → 穿透
3. **基线污染入口（报告没写，它复现时自己发现的）**：`push()` 一进门就 `this._last = s`，
   **在守卫之前** —— NaN 样本顶掉基线后，紧随其后的**合法**样本也算成 NaN 被丢弃，
   于是"合法包/NaN包"交替上报时**检测彻底失明**

第 3 条比"清零连击"严重得多（清零至少还会触发惩罚，失明则是完全无感），
**而且原报告没写**。能挖到这一层，说明是真跑了代码而不是照单施工。

我逐条核过基线源码确认属实：

```
基线 172:  const prev = this._last;
基线 173:  this._last = s;        ← 在守卫之前，声明属实
修复后 191:  this._last = s;      ← 已移到守卫之后
```

## 7. 对 2 项"待总审裁决"的独立意见

### P1-13 · `spatial` 的 `capacity` 声明未实现

W1-B 倾向**方案 B（删除字段）**，理由："写了但没实现"比"没有"更糟，会让人拿它做内存预算。

**我认同 B，但建议先做一件事：查全库有没有调用方真的传了 `capacity`。**

- 若**无人传** → 删除零成本，直接删
- 若**有人传** → 那些调用方当前以为有保护，实际没有，**编译报错正是把他们揪出来的最好时机**

补充一点 W1-B 没提的：原 JSDoc 写的是「**初始容量提示**」。
如果只是"提示"（hint，类似 `Map` 的 capacity hint），那么不实现**算不上契约违背**——
hint 本来就是可选优化。真正的问题在于字段名 `capacity` 太像硬约束，
**语义与命名不符**。所以若选 B，建议同时在 CHANGELOG 里说明"这是 hint 不是上限，已移除以免误解"。

若总审选 A（实现为硬上限），我**同意 W1-B 的判断：应拒绝并抛错，不要静默淘汰**。
空间索引里丢一个条目的表现是"某个实体突然不再被任何查询命中"，比崩掉难查一个量级。

### P1-3 · loop 音效不可抢占

**我支持维持现状**（W1-B 的处理正确）。理由补充一条：
loop 音效通常是 BGM / 环境音这类**长期占用**的资源，允许被抢占会导致
"背景音乐播到一半被一声脚步声挤掉"，体验上比"新音效被拒"更糟。
README 已写明 + 既有测试已锁住，维持现状的成本最低。
