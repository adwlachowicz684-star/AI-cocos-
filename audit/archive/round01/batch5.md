## 4. 审核清单（逐项过，别跳）

按下面的六类逐项检查。**每个单元都要过一遍全部六类**，不能只挑自己擅长的。

### A. 静默错误（本库最痛恨的一类，优先级最高）

这类 bug 的共同点：**不报错、不崩溃，只是结果不对**，排查时没人会想到源头。

- [ ] **NaN / Infinity 穿透**：`Math.max/min` 不做有限性检查（`Math.max(1, NaN) === NaN`）；
      一个 NaN 帧能让坐标永久变 NaN 且不报错
- [ ] **缺值被当成 0**：`Number(null) === 0`、`Number('') === 0`、`Number([]) === 0`；
      容量字段因此归零（撤销栈永不裁剪 → 内存无限增长）
- [ ] **除零 / 退化区间**：`a === b` 时除零；`min > max` 的区间；空数组求最值得 `∓Infinity`
- [ ] **dt 守卫**：负数 / NaN / Infinity 的 dt。
      注意 `dt <= 0` 挡不住 NaN，`!(dt > 0)` 挡不住 Infinity
- [ ] **索引越界静默**：`arr[i]` 越界得 `undefined`，`undefined.xxx` 才崩，中间可能已污染数据
- [ ] **浮点相等**：`===` 比较浮点数；累积误差
- [ ] **空 catch / 静默降级**：`catch {}` 吞掉异常；失败时返回默认值让坏数据看起来正常
- [ ] **`slice`/`splice` 的负数参数**：`slice(0, -1)` 是"去掉最后一个"，不是"取 0 个"
- [ ] **原型链污染**：`Record<string, T>` 按键查表时取到 `Object.prototype` 上的方法

### B. 生命周期与泄漏（rule5）

- [ ] `destroy()` 是否存在、是否清干净：**事件监听、定时器、缓存引用、创建的节点**
- [ ] 最容易漏的是**事件监听**和**定时器**——它们不随对象消失，而是继续持有 `this`
- [ ] `destroy()` 后再次调用其他方法是否安全（幂等 / 状态一致）
- [ ] 长期运行的容器是否只增不减（缓存、历史记录、撤销栈、连接池）
- [ ] 对象池语义：`active` 计数会不会变负；重复归还；借出不还

### C. 契约一致性（注释说谎比没注释更糟）

- [ ] **JSDoc 与实现是否一致**（逐条比对参数、返回值、边界行为）
- [ ] **README 与源码是否一致**（API 表里的函数是否真的存在、签名是否对得上）
- [ ] 是否存在**记录为"设计如此"但实际是 bug** 的行为（本库已出现 2 例，见第 2 节）
- [ ] 文档里写了但源码里没有的 API（**漏写你会去看源码，写错你会信文档**）
- [ ] 同名不同义：同一概念两套命名 / 同一命名两套语义

### D. 架构铁律（rule1-7）

- [ ] rule6 横向依赖：是否 import 了其他插件（允许 `_core` / `ds`）
- [ ] rule1 业务耦合：是否出现游戏专属概念（应通过注入/配置解耦）
- [ ] rule4 配置驱动：魔法数字是否硬编码
- [ ] rule7 是否自带 README + 测试 + 示例

### E. 性能陷阱

- [ ] **O(n²) / 二次遍历**：先取结果再逐个反查（见第 2 节 queryCircle 案例）
- [ ] **展开栈溢出**：`Math.max(...xs)`、`f(...args)`，数组超 10 万项直接 `RangeError`
- [ ] **热路径分配**：每帧 `new` 对象 / `Array.from` / 闭包
- [ ] **无限 while / 死循环**：循环变量非有限值时条件恒真（如 `Infinity - 2π` 仍是 `Infinity`）
- [ ] **递归深度**：无上限的递归

### F. 数值与配置健壮性

- [ ] 容量/上限类字段是否用 `clampNum` 收口（防内存无限增长）
- [ ] 普通配置类字段是否用 `numOr` 收口（只兜非有限值，不定上界以免误伤合法值）
- [ ] 随机数是否走 `IRandomSource` 注入（可复现 + 可测试），而非裸 `Math.random`
- [ ] 存档 / 配置反序列化后的字段是否做了有效性校验
